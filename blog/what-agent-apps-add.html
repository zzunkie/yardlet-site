What desktop apps for coding agents add to Claude Code and Codex

An app that runs several agents has to know when each one is working, waiting or done. Nine apps solve it with global hooks, command wrappers, a terminal signal or the agent's own protocol, and some add prompt text or skip permission checks by default. What each does as of November 13, what it leaves on your Mac, and its memory at rest.

I make Yardlet, a free, open-source Mac app that runs coding agents like Claude Code and Codex in one window. So I make one of the apps in this post, and you should read it with that in mind. I've linked every claim to the app's own code at a fixed commit or to its documentation, as of November 13, 2026. Where I couldn't find out, I say so.

An app that runs several agents at once has to know what each one is doing: working, waiting for you, or done. Claude Code and Codex were built to be used directly, so each desktop app picks its own way to find out. That choice decides what the app adds to the agent and what stays on your Mac after you stop using it.

Apart from Yardlet, each app here is a commercial product or part of an open-source project with at least 10,000 stars on GitHub.

#How an app finds out what the agent is doing

Hooks in the agent's own settings. Claude Code and Codex both run commands you register at points in a session: when a turn ends, when the agent needs permission, when it sends a notification. Both document this as an extension point. Claude Code reads hooks from ~/.claude/settings.json for every project, from a project's .claude/settings.json and a few other places (docs); Codex reads them from ~/.codex/hooks.json or a [hooks] table in ~/.codex/config.toml, and asks you to review and trust a hook before it runs (docs). A hook registered there tells the app exactly when a turn ends or a permission prompt appears, even when the agent runs as its normal terminal UI, and it works for any agent that has hooks. The catch is where it lives. A hook in your global settings runs in every session of that agent, including the ones you start in Terminal with the app closed, and it stays after you drag the app to the Trash unless something removes it. Orca and Paradev (Superset until October) work this way, and both make their hooks exit at once outside their own terminals.

Hooks for one process. A terminal app can put its own claude and codex in front of the real ones in the shells it opens, as a shell function or a script early on PATH. The wrapper then hands the agent hooks for that process only: Claude Code takes extra settings with --settings <file> (CLI reference), and Codex takes config overrides with -c. cmux does this, and leaves your settings files alone. The cost is that the command you type isn't quite the command that runs. In May a cmux release added --allow-dangerously-skip-permissions to every claude launch so a button could switch to bypass mode later. The flag doesn't turn bypass on by itself (Yardlet passes it too; see note 25 below), but in the terminal UI it sent ordinary claude starts down Claude Code's dangerous-mode path, as the fix describes. A user reported it about an hour after the release, and the maintainer removed it the same day.

A signal from the terminal. Claude Code 2.1.295 added the Program Status Protocol, an escape sequence (OSC 7501) that tells a terminal whether it's working, waiting on you, or done, and Codex reports it too since a change merged in October. A terminal app that reads it needs nothing installed anywhere. The Herdr app relies on it alone; cmux and Orca read it alongside their hooks. It only works with recent versions of the agents, and it carries the state, not what the agent is waiting for.

The agent's own protocol. Claude Code can run as a process that reads and writes JSON events (-p --input-format stream-json --output-format stream-json), which is also how the Claude Agent SDK drives it. Codex has an App Server that speaks JSON-RPC, the interface its VS Code extension uses. Many other agents speak the Agent Client Protocol. An app that drives the agent this way gets turns, tool calls and approval requests as data, so it needs no hook and no wrapper. T3 Code, Paseo, Vibe Kanban and Yardlet work this way, and Orca and Paradev use it for their chat views. The cost is on the app's side: it draws the conversation itself instead of showing the agent's own terminal UI, it supports only agents that have such a protocol, and it waits on whatever the protocol doesn't expose yet.

#What else comes along

Knowing the agent's state is only part of it. Some apps also add their own text to the system prompt, so the agent knows it's inside the app: how to link a pull request, how to hand work to another agent. It works, and it means the agent you talk to isn't quite the one in its own app. Some install skills into the agent's global skills folder. Some mark their folders as trusted in the agent's config. And several start every session with the agent's permission checks off. Claude Code otherwise asks before running commands, and Codex runs in a sandbox and asks before going outside it (Codex docs).

A few things stood out. The apps that put hooks in your global settings have also built ways to undo it: Paradev added its guard and switch after a user report, Orca removes its hooks when you turn them off, and Paseo's terminal hooks are off until you turn them on. cmux shows that hooks don't have to live in your settings at all. And four of the nine apps start sessions with approvals and the sandbox off unless you change it.

#Yardlet, the same way

Yardlet runs Claude Code with --print --input-format stream-json --output-format stream-json and Codex as app-server --stdio; OpenCode, Antigravity, Kimi Code, Grok Build and Hermes go over ACP (Claude, Codex). It registers no hooks and writes nothing into ~/.claude, ~/.claude.json or ~/.codex. Its terminal panel starts your login shell with four variables (TERM, COLORTERM, and cat as PAGER and GIT_PAGER) and nothing in front of the agent commands (source).

Here is what it adds:

  • Its MCP server. Each Codex, Claude Code and ACP session Yardlet starts gets yardlet-mcp through that session's own option, which I wrote about in an earlier post. The agent then sees the server's instructions, about 900 characters on how to use the browser and task tools (text), and the descriptions of up to 46 tools of its own, 21 of them for the browser (list), plus the tools of any connectors you've signed in to.
  • Turning the tools off. Settings › General › Agent browser tools takes the browser tools (20, or 21 with a saved password) out of sessions started afterwards (setting), Share the terminal with agents removes one more, and a connector can be turned off for a task. The other 24 tools and the instruction text stay: there is no switch yet that starts a session without the server (source).
  • Codex's permission. Yardlet sets it on each thread, Ask for approval unless you pick another, so a default in your config.toml applies only with Custom (note 25).
  • Yardlet instructions. Text you write in Settings goes to every agent you start, appended to Claude Code's system prompt and as Codex's developer instructions. It's empty unless you write something, and Yardlet adds no words of its own to it (source). One exception: an optional daily routing evaluation, off by default, adds a short note on which agent and model to use for which kind of work when you turn it on (default).

The protocol route has its costs here too. Cursor Agent, Pi and Muse Code have no way to take an MCP server for one session, so their tasks in Yardlet run without its tools. Yardlet shows a conversation it draws itself, not Claude Code's or Codex's terminal UI.

#Memory at rest

The last column of the table comes from the post I published on November 11, measured on November 9 and 10 on one MacBook Pro (M1 Pro, 16 GB, macOS 15.6.1). Each app was opened for the first time in an empty home folder, left alone for a minute and sampled for two; memory is the phys_footprint sum of every process macOS charges to the app, the number Activity Monitor shows. The agent CLIs were stand-ins and aren't counted, which leaves out the Codex App Server Yardlet starts at launch. Conductor and Superset (now Paradev) were measured at their sign-in screens, and cmux was playing its welcome video; on a second launch it used 168 MiB. Vibe Kanban wasn't in that run.

With ten tasks streaming at once, Yardlet used 214 MiB, T3 Code 867 MiB and Paseo 987 MiB; the others weren't run under load. That post has the per-run data, where Yardlet does worse, and what the numbers leave out.

#What this doesn't cover

I read code and documentation; I didn't run each app and watch what it wrote, except for the hands-on notes behind the memory post. I couldn't check Conductor's code, and what happens to these files when you delete each app isn't documented anywhere I found, so I've left it out of the table. All of these apps ship every few days. If something here is wrong or out of date, open an issue and I'll correct it in the post with the date.
